1. 结论摘要

综合评分：61 / 100。难的部分（并发协议）做对了，简单的部分（边界防御、并发测试）反而没做。作为技术探索或面试作品约 75 分，作为生产组件约 40 分。分项理由见 第 11 节。

设计评价。这是一个开放寻址（线性探测）+ 每槽位 64 位"复合键"的哈希表。复合键里同时放了业务键（54 bit）和一个嵌入式读写锁（1 bit 写标志、1 bit 删除标志、8 bit 读者计数），所有状态转换都用 Interlocked.CompareExchange 完成。核心并发协议是正确的：我用带版本号的载荷做了 5 秒高强度压力测试，2,117 万次成功读取中没有出现一次撕裂读。

但它不是严格意义上的"无锁"（lock-free），而是"用 CAS 实现的、按槽位划分的读写自旋锁"。持有写标志的线程被抢占、抛异常或阻塞时，其他线程会在该槽位上无限自旋。这一点直接导致了下面的几个严重问题。

级别问题证据
P0表满时 TryGet/TryDelete/TrySet 对不存在的键无限循环实验 E2：3 秒超时仍未返回
P0删除只打墓碑、永不回收：累计写入过 N 个不同键后，即使全部删除也无法再插入（死循环）实验 E3

关于 README 的结论"如果键能组合成 64 位整数，用 ConcurrentDictionary 就好"。在"值不可变、可以共享引用"的前提下，这一结论成立（读吞吐 CD 19.1 M/s vs CAS 10.8 M/s）。但原性能测试并没有比较同一语义：一旦要求写入时拷贝值（CAS 表的真实语义），ConcurrentDictionary 因为 GC 写屏障/卡表开销，更新吞吐只有 0.49–0.57 M/s，CAS 表是 9.48 M/s（约 17–19 倍）。CAS 设计真正的优势是预分配、原地覆写、不产生 GC 压力，而这个优势恰好没有被原测试测到。详见 第 8 节。

3. 数据结构与位布局

3.1　64 位复合键 compondKey

代码中的实际布局（高位在左；注意 README 写的是"54 bytes"，实为 54 bit；readme.txt 的位编号方向与代码相反）：

linkId22 bit · 63–42
clcId18 bit · 41–24
sbp14 bit · 23–10
W
D
readers8 bit · 7–0
bit 63bit 0
W = doWrite（bit 9，0x200）写者独占标志 D = isDelete（bit 8，0x100）墓碑标志 readers（bit 0–7，0xFF）并发读者计数 0–255 
// KeyIn54BitCASHashTable.cs:44
public long GenerateKey(long linkId, long clcId, long sbp)
    => (linkId << 42) | (clcId << 24) | (sbp << 10);   // 低 10 位恒为 0，留给 W / D / readers

注意：linkId 占到第 63 位（符号位）。linkId ≥ 221 时键为负数，而 linkId = 221、其余为 0 时键恰好是 long.MinValue（见 P1-1）。

3.2　代码中的"魔法常量"解码

常量十六进制含义用于
0x200…0000 0010 0000 0000W 位加写锁
0x100…0000 0001 0000 0000D 位删除、判断已删除
-2570xFFFF…FEFF清 D更新时"复活"已删除项
-5130xFFFF…FDFF清 W释放写锁
-7680xFFFF…FD00清 W + readers，保留 DUpdate 的期望值：无写者、无读者
-7690xFFFF…FCFF清 W + D，保留 readersGet / Delete 的期望值：无写者、未删除
-10240xFFFF…FC00清低 10 位KeysAreEqual：只比较业务键

3.3　槽位数组与内存布局

构造函数一次性分配 arrayLength 个 Entity（24 字节：long + 引用 + int + 填充），并为每个槽位单独 new byte[contentLength]。测试配置 arrayLength = 10,107,313（质数）、contentLength = 256：

要点：Update 要求 readers = 0 且 W = 0 才能成功，所以只要读者持续进入，写者就一直失败（读者优先 → 写者饥饿，P1-4）。Update 会把 D 清零，因此 TrySet 可以"复活"已删除的键。

每次读取要对共享的键字做至少 2 次 CAS 写操作。对同一热点键，这意味着所有读者都在争抢同一条缓存行（缓存行乒乓）。这也是单热点键场景下 CAS 表读吞吐远低于 ConcurrentDictionary 的根本原因（复现：CD 5,878 万 vs CAS 370 万 RPS）。

5. 并发协议本质：嵌入键中的"读写自旋锁"

把各操作 CAS 成功所需的前置条件列出来，协议的性质就很清楚了：

操作要求 W要求 D要求 readersCAS 后相当于
新增槽位整体为 0key + W获取写锁
读取00任意（<255）readers + 1获取读锁
更新0任意0W = 1, D = 0获取写锁
删除00任意D = 1单次原子标记
  • 读写互斥是正确的。写者持有 W 时，读、删、其他写的 CAS 都必然失败；读者持有计数时，更新必然失败。Interlocked 在 .NET 中是全栅栏，所以内容写入对随后获得读锁的线程可见。实验 E7 用"8 字节版本号重复填满整个载荷、长度随机"的方式检测撕裂读：21,174,067 次成功读取，0 次不一致。
  • 但它是阻塞算法。无锁（lock-free）的定义是"任一线程被挂起都不妨碍其他线程继续推进"。这里持有 W 或读者计数的线程一旦被操作系统抢占、异常退出或卡在 GC 上，其他线程就只能自旋等待。"没有用 lock 关键字"不等于"无锁"。
  • 读是写。每次读取都修改共享字，热点键下缓存行在核之间来回迁移，读扩展性差；这也使得 8 位读者计数成为一个硬上限。
  • README 提到的上交所原型里值是 64 位整数，可以和键一起原子读写，那种场景下天然没有"大值拷贝"的临界区；移植成 256 字节值后，才引入了读写锁语义和它带来的所有问题。

6.2　性能测试的设计问题

(a) 验证方式无法发现并发错误

更新线程写回的内容与原值完全相同（record[index].url），所以即使发生撕裂读或丢失更新，ResultMatch 仍然会成立。而且 ResultNotMatch 只打印，从不 Assert，测试永远"通过"。

(b) 计时方式与结果口径

  • 每次调用都包一对 Stopwatch.Start()/Stop()，本机实测单对开销 ≈ 34 ns，与被测操作（~100 ns）同量级。在 CD 单键读取测试中，每次调用计时约 67 ns，其中一半是秒表本身。
  • RPS 计算方法为 Σ(每线程调用次数 / 该线程的 API 累计时间)，并不是墙钟吞吐。
  • 12 个任务调用次数不同（读 3M、写 6M、删 15M），完成时间也不同。例如复现中 CD 随机测试：读线程 5 秒就结束了，删除线程跑了 24 秒，所以"并发混合"只存在于前 5 秒。因此"成功率"随调度变化很大：CD 随机读成功率在原报告中为 96.1%，本机复现为 99.9%。
  • 发生异常时 internalStopWatch 不会 Stop，result 也不会重置，上一次的结果会被重复计数。
  • 线程内部的局部计数器用 Interlocked.Increment 是多余开销；Task.Run 启动 12 个任务依赖线程池注入，不保证同时开始。

(c) 两边比较的不是同一件事

CAS 表ConcurrentDictionary 测试
写TrySet：插入或更新，把 256 B 缓冲区内容拷贝进槽位TryAdd：仅在不存在时插入，80–97% 的调用什么都不做；只存引用，不拷贝
读分配新数组并拷贝返回内部引用（调用方可以篡改表内数据）
删打标记，槽位保留真正移除节点
"成功率"语义不同，互相比较没有意义（例如 TrySet 成功率 100% vs TryAdd 3.4%）

为什么"CD + 拷贝更新"这么慢？实验 E14 做了归因。只分配、不存入：28.4 M/s。存入但复用旧引用、不分配：10.7 M/s。存入新分配的数组：0.57 M/s，期间发生 341 次 Gen0 GC 和 6 次 Gen2 GC。原因是老年代的 300 万个节点不断指向新生代对象，写屏障标脏卡表，每次 Gen0 GC 都要扫描大量卡片，还会提升对象、触发 Gen2。CAS 表把值原地拷进预分配缓冲区，完全没有这个问题，这才是它真正的价值所在。

结论修正：如果值是不可变的（string 或只读 byte[]）、可以共享引用，就用 ConcurrentDictionary<long, T>，简单且读更快（19.1 vs 10.8 M/s）。如果值必须以固定长度缓冲区原地更新，且写占比不低、对 GC 停顿敏感，CAS 这类预分配设计有数量级优势（混合负载 10.07 vs 1.54 M/s），前提是修掉第 9 节的问题。

9. 问题清单（附实测证据）

9.1　正确性 / 可用性

P0-1　表满时查找和插入无限循环

HashSearch（Base.cs:187–191）和 AddOrUpdate（Base.cs:60–64）的探测循环只以"遇到空槽"或"键相等"为终止条件，没有探测次数上限。表满后，对不存在的键做 Get、Delete 或 Set，都会让线程 100% 占用一个 CPU 核并永远不返回。

E2 arrayLength=7，插入 7 个键后： TryGet(missing) 3 秒内返回: False => 死循环 TryDelete(missing) 3 秒内返回: False TrySet(new key) 3 秒内返回: False => 死循环

修复：探测次数上限设为 arrayLength，超出时返回"表满"或"不存在"；插入时维护计数，超过装载因子阈值即拒绝或扩容。

P0-2　墓碑永不回收：容量按"历史上出现过的不同键数"计算

删除只置 D 位，槽位永远不回到 0（图 4-6）。短链接服务里键会持续新增，被删除的键又永远占着槽位，所以表迟早会"被墓碑填满"并触发 P0-1。墓碑还会拉长所有探测链，让查找越来越慢。

E3 arrayLength=11：依次 插入+删除 11 个不同键（存活数 = 0） TrySet(第 12 个键) 3 秒内返回: False => 死循环

修复：插入时如果确认键不存在，可以复用探测链上遇到的第一个"D=1 且 readers=0"的墓碑。要避免同一个键被两个线程插到两个不同墓碑上，需要"占位 + 复查"的两阶段协议。更简单可靠的做法是定期重建：把存活项复制到新表，再用一次 Volatile.Write 原子替换引用。

P0-3　临界区异常 → 槽位被永久锁死

AddOrUpdate 和 Update 在持有 W 位期间调用 Buffer.BlockCopy，却没有 try/finally 释放 W 位；TryGet 在持有读者计数期间 new byte[]（可能 OOM），同样没有保护。代码作者注释掉的 CASFailureException 和 ResetDoWriteBit() 说明作者意识到了这个问题，但没有实现。

E4 通过基类 public API 写入 17 字节内容（上限 16）： base.TrySet 抛出 ArgumentException 随后 TryGet 同一键 3 秒内返回: False => 永久自旋 随后 TrySet 合法内容 3 秒内返回: False （更新路径同样复现）

修复：所有"获取 → 操作 → 释放"都放进 try { … } finally { Release(); }，并把可能抛异常的校验和分配移到获取锁之前。

P1-1　合法输入触发 OverflowException

包装类允许 linkId ≤ 4,194,303（22 位），而 2097152 << 42 = 263 在 long 中就是 long.MinValue。Hash() 使用 Math.Abs(key)（Base.cs:200），对 MinValue 会抛异常。

E1 GenerateKey(2097152,0,0) = -9223372036854775808 TrySet 抛 OverflowException: Negating the minimum value of a twos complement number is invalid. TryGet 抛 OverflowException

修复：(int)((ulong)key % (ulong)arrayLength)，或者先 key >>> 10 再做乘法散列（见第 10 节）。

P1-2　基类 public API 绕过全部校验

派生类的 3 参数重载并没有隐藏基类的 TrySet(long key, byte[])、TryGet(long key, …)、TryDelete(long key)，这些方法都是 public。它们不检查键的低 10 位、键是否为 0、内容长度或 null。

E4 base.TrySet(0, "zero") 返回 0（"新增成功"） base.TryGet(0) 返回 -2（"不存在"）=> 静默丢数据 （键 0 时 final = 0，槽位被写回"空"，但内容已写入）

低 10 位不为 0 的键会让 key + doWrite 进位，污染业务键。修复：把基类方法改为 protected（或 internal），并在基类里做最低限度的防御性检查。

P1-3　8 位读者计数溢出以异常形式暴露给调用方

读者上限 255。在 8 核机器上，只要线程数远超核心数（例如 ASP.NET 线程池在高负载下扩张），被抢占在读临界区内的线程就会累积起来。

E9 400 个线程读同一个键 5 秒：成功 31,717,714 次，ReaderCounterOverflowException 265,636 次

WebApi 调用方只会看到 500 错误。修复：计数满时自旋等待（SpinWait）而不是抛异常；或者改用 seqlock，读者不写共享状态（第 10 节）。

P1-4　读者优先 → 写者饥饿，尾延迟不可控

Update 要求 readers 恰好为 0。读者之间的持有区间只要有重叠，写者就一直 CAS 失败。

9.2　性能 / 资源

P2-1　无退避自旋，超额订阅时吞吐下降

所有 CAS 重试循环都是紧循环，没有 SpinWait、Thread.Yield 或 Pause。持锁线程被抢占后，其余线程会把整个时间片烧在自旋上。

E12 单热点键，75% 读 / 25% 写：8 线程 2.10 M ops/s；64 线程 1.07 M ops/s（下降 49%） 两组各运行 3 秒，但整个实验实际耗时 89.5 秒：发出停止信号后，自旋线程迟迟无法全部退出

代码末尾的中文 TODO（Base.cs:342–346）也提到应统计重试次数，但没有实现。

P2-2　内存：1010 万个独立 byte[]，按最大长度预分配

E11：托管堆 +2.86 GB，构造 7.1 秒，每次完整 GC 要遍历 1010 万个对象（698 ms 停顿）。实际 URL 平均约 40 字节，却按 256 字节预留，只用了约 15%。Entity 为 24 字节，一条缓存行放不下 3 个槽，相邻热点键之间还存在伪共享。

修复：用一整块 byte[arrayLength * contentLength]（GC.AllocateUninitializedArray(pinned: true)）或 NativeMemory 作为数据区，槽位只存偏移；这样只有 1 个大对象，GC 几乎零成本。

P2-3　哈希函数与表长

  • 键的低 10 位恒为 0。构造函数不强制质数长度，一旦传入 2 的幂，所有键都挤进极少数起始槽。E5：长度 65536 时，20,000 个键只落在 64 个不同起始槽上，插入慢 10 倍；65537（质数）时则是 20,000 个。
  • 线性探测对聚集敏感。E6：均匀随机键在 0.3 装载因子下最长探测链为 19。
  • README 称"装载因子 0.5 时平均查找 1.1 次"，但 readme.txt 自己按线性探测公式算出的是 1.5 次（成功）/ 2.5 次（失败）。测试实际装载因子是 0.3，实测为 1.045（测试数据）/ 1.212（随机键）。
  • 取模运算（%，64 位除法 ~20–40 周期）可以换成 2 的幂表长 + 乘法散列（Fibonacci hashing）。

P2-4　TryGet 每次分配新数组

读路径每次 new byte[len]，在高 QPS 下产生持续的 Gen0 压力。建议提供 int TryGet(key, Span<byte> destination)，让调用方复用缓冲区。

9.3　代码质量 / 文档

P2-5　API 与可维护性

  • 返回值用魔法数字（0/1/-2/-3），测试里还统计从不存在的 -1。应改成 enum SetResult { Added, Updated } 和 enum GetResult { Found, NotFound, Deleted }。
  • 参数错误抛出 ArgumentOutOfRangeException("KeyIsZero Error…")，却把消息放进了 paramName 参数；ArgumentNullException("contentLength") 的参数名也写错了（应为 content）。
  • 位掩码用十进制负数（-257、-768、-769、-1024）表达，可读性差。应定义 const long WriteBit = 1L << 9 等具名常量。
  • 未使用的代码：CheckWriteBitIsZero、CheckReaderCounterIsMinimum、CASFailureException，以及大量注释掉的代码。
  • AddOrUpdate 用递归重试，可以改为循环；HashSearch 的 i 从 0 开始，第一次探测重复访问了起始槽（与 AddOrUpdate 从 1 开始不一致）。
  • Hash、Collision、KeysAreEqual 是 public 却属于实现细节。
  • 拼写：compondKey → compoundKey、Invild → Invalid、Nubmer、totoalRecord 等。

P2-6　Update 读取当前值的时机

Update 在循环里每次重新读 compondKey 来构造期望值（源码中的 ToDo 说可以移到循环外）。实际上正是因为每次都重新读，才能正确保留 D 位，所以不应按 ToDo 那样移出循环。这里需要在注释里说明。

P2-7　文档与实现不一致

  • README："54 bytes / 1 byte / 8 byte" 应为 bit。Excel："265 byte arrays" 应为 256，且实际数据约 40 字节。
  • readme.txt：位编号方向与代码相反；表长 6,080,023 与代码中的 10,107,313 不同；冲突公式写成 /，应为 %；Get "返回 URL 或 null" 与实现不符。

10. 改进建议与示例代码

10.1　最小修复（不改变整体设计）

// 1) 安全哈希：不会溢出；先去掉恒为 0 的低 10 位再混合
private int Hash(long key)
{
    ulong h = (ulong)key >> 10;
    h *= 0x9E3779B97F4A7C15UL;              // Fibonacci hashing
    return (int)(h % (ulong)arrayLength);   // 或 2 的幂长度下：(int)(h >> (64 - bits))
}

// 2) 有界探测：最多探测 arrayLength 次
private bool HashSearch(long key, out int index)
{
    int home = Hash(key);
    for (int i = 0; i < arrayLength; i++)
    {
        index = home + i; if (index >= arrayLength) index -= arrayLength;
        long k = Volatile.Read(ref entityArray[index].compondKey);
        if (k == 0) return false;
        if (KeysAreEqual(key, k)) return true;
    }
    index = -1; return false;                // 表满且不存在
}

// 3) 临界区用 try/finally 保证释放；带退避的自旋
private int Update(int index, ReadOnlySpan<byte> content)
{
    ref long slot = ref entityArray[index].compondKey;
    var spin = new SpinWait();
    long locked;
    while (true)
    {
        long cur = Volatile.Read(ref slot);
        long expected = cur & ~(WriteBit | ReaderMask);
        locked = (expected | WriteBit) & ~DeleteBit;
        if (Interlocked.CompareExchange(ref slot, locked, expected) == expected) break;
        spin.SpinOnce();                     // 超额订阅时会让出 CPU
    }
    try
    {
        content.CopyTo(entityArray[index].content);
        entityArray[index].contentLength = content.Length;
    }
    finally
    {
        Volatile.Write(ref slot, locked & ~WriteBit);   // 持锁期间无人能改，普通写即可
    }
    return 1;
}

10.2　结构性改进：用 seqlock 替代读者计数

把 8 位读者计数换成版本号：写者把版本加 1（变奇数，表示正在写）→ 写内容 → 再加 1（变偶数）。读者不写任何共享状态：先读版本，是偶数就拷贝内容，拷完再读一次版本，两次一致则成功，否则重试。

  • 读不再修改缓存行，热点键的读可以线性扩展（解决单键读 370 万 vs 5,878 万 RPS 的差距）。
  • 没有读者计数，也就没有 255 上限（P1-3），写者无需等待读者（P1-4）。
  • 代价：读者可能读到"写了一半"的内容，但会被版本校验发现并丢弃重试。拷贝必须拷进私有缓冲区，拷贝前后都要有正确的内存屏障（Volatile.Read / Interlocked.MemoryBarrier）。
// 读者（示意）
while (true)
{
    long v1 = Volatile.Read(ref slot.Version);
    if ((v1 & 1) != 0) { spin.SpinOnce(); continue; }       // 写者进行中
    int len = slot.Length;
    data.AsSpan(slot.Offset, len).CopyTo(dest);                // 拷到私有缓冲区
    Interlocked.MemoryBarrier();
    if (Volatile.Read(ref slot.Version) == v1) return len;    // 版本未变：读取有效
}

10.3　其他建议

  • 容量管理：维护存活数和墓碑数，超过阈值时后台重建新表（只拷存活项）并原子切换引用；或者至少在达到阈值时拒绝插入，并通过日志或指标报警。
  • 内存布局：单块数据区 + 槽位只存 key、版本、长度；按缓存行对齐热点字段。
  • API：枚举返回值；Span<byte> 读写接口；基类实现细节改为 private/protected；sealed 包装类。
  • 可观测性：按 Base.cs 末尾 TODO 的想法，统计 CAS 重试次数分布、最长探测长度、墓碑比例。

10.4　测试改进

  • 加入并发不变量测试（可直接改造附录中的 E7）：写入"版本号重复填充 + 随机长度"的载荷，读者校验一致性，并用 Assert.AreEqual(0, torn) 断言。
  • 边界测试：long.MinValue 键、表满、墓碑满、小表强制冲突、内容长度 0 或等于上限、基类 API（或确认它们不再 public）。所有可能挂死的测试都加 [Timeout]。
  • 功能测试使用小表（如 4139 槽），把单元测试从 2 分钟降到秒级；大表只在性能测试中使用。
  • 性能测试改用 BenchmarkDotNet（单线程微基准），以及"整段计时 + Barrier 同时起跑 + 固定时长"的多线程吞吐测试；对照组使用相同语义（upsert + 拷贝）；报告 p50/p99/p99.9 延迟，而不是每次调用都掐秒表。
  • 测试数据使用均匀随机键（或真实分布），并单独测试高冲突场景。
  • 可以考虑用 Microsoft Coyote 等工具做系统化的并发调度探索。

补上第 10.1 节的最小修复（大约一两百行），再按 10.4 节加入并发不变量测试和边界测试后，评分可以提到 75–80 分。
